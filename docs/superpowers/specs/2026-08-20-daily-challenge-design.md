# CubeStats: the daily challenge and leaderboard

Date: 2026-08-20
Status: draft, not yet approved

Phase 2 of three. Phase 1 (profiles and usernames) is a prerequisite and is
specified separately; this document assumes `profiles.username` and
`profiles.opted_in` exist.

## Problem

Every solve in CubeStats is private and every scramble is unique to the person
who generated it. There is no way to compare yourself to anyone, and no reason
to open the site on a day you do not feel like practising.

## Goals

- One scramble per event per day, identical for everyone.
- One committed attempt at it, so the ranking reflects a cold solve.
- A board showing who was fastest, with the scramble visible so anyone can
  attempt the case themselves afterwards.
- An unranked "best today" column from ordinary practice, for people who
  do not want to compete.
- Nobody appears on the board without opting in.
- The existing timer keeps working offline, signed out, and unchanged.

## Non-goals

Friends, profiles and shared practice calendars (phase 3). Historical boards
beyond the current day, all-time records, streaks, comments, and moderation
tooling beyond a manual SQL takedown. Inspection time. Multi-round events.

## Decisions taken before this draft

| Decision | Choice |
| --- | --- |
| What is ranked | The shared daily scramble |
| Unranked column | Personal best from ordinary solves that day |
| Who can read the board | Anyone signed in |
| Who appears on it | Opt-in only |
| Attempts | One, committed on reveal |
| Day boundary | UTC |

## The central constraint

One committed attempt means **the scramble must be unreadable until the
attempt is committed**. Row Level Security cannot express that: a policy can
decide whether you may read a row, but it cannot record that you did. If
`daily_scrambles` were selectable by authenticated users, anyone could read
today's scramble, practise it, and then "commit".

So reads of the scramble go through a `security definer` function that writes
the commitment and returns the scramble in the same transaction. The table
itself has no select policy at all.

The second consequence is that scrambles cannot be generated by clients. A
client-supplied scramble could be four moves from solved, and Postgres cannot
validate one — checking a random-state scramble needs cubing.js's wasm solver.
Generation therefore moves server-side, which introduces the first
non-browser code in this project.

## Architecture

```
Supabase Edge Function (Deno + cubing.js)   -- daily, service role
      | writes
daily_scrambles          (no client select policy, ever)
      ^
      | security definer RPC: reveal_daily()  -- commits, then returns
Client
      | security definer RPC: submit_daily()  -- one submission, immutable
      v
daily_attempts  ---- published rows ----> board (public select)
daily_bests     ---- published rows ----> board (public select)
```

The local-first model is untouched. A challenge solve is recorded in the
normal local store like any other solve; submission is an additional,
separate write. The timer never waits on the network.

## Data model

```sql
-- One row per event per UTC day. Written only by the Edge Function's
-- service role; no client may select from it directly.
create table daily_scrambles (
  event       text not null,
  utc_day     date not null,
  scramble    text not null,
  created_at  timestamptz not null default now(),
  primary key (event, utc_day)
);

-- The commitment and its result. Inserted by reveal_daily(), completed once
-- by submit_daily(), and never updated again.
create table daily_attempts (
  user_id       uuid not null references auth.users(id) on delete cascade,
  event         text not null,
  utc_day       date not null,
  revealed_at   timestamptz not null default now(),
  submitted_at  timestamptz,
  time_ms       integer,
  penalty       text not null default 'none'
                  check (penalty in ('none', 'plus2', 'dnf')),
  published     boolean not null default false,
  primary key (user_id, event, utc_day)
);

-- The unranked column: the best ordinary solve that day. Unlike an attempt
-- this is mutable, because the underlying solve can be penalised or deleted.
create table daily_bests (
  user_id     uuid not null references auth.users(id) on delete cascade,
  event       text not null,
  utc_day     date not null,
  time_ms     integer not null,
  scramble    text not null default '',
  updated_at  timestamptz not null,
  published   boolean not null default false,
  primary key (user_id, event, utc_day)
);

create index daily_attempts_board on daily_attempts (event, utc_day, time_ms)
  where published and submitted_at is not null and penalty <> 'dnf';
create index daily_bests_board on daily_bests (event, utc_day, time_ms)
  where published;
```

`effective_ms` (the +2 adjustment) is computed on read, matching
`types.ts:effectiveMs` rather than duplicating the rule in SQL.

### Which events

The challenge runs for events that are a distinct puzzle: `222`, `333`, `444`,
`555`, `666`, `777`, `minx`, `pyram`, `skewb`, `sq1`, `clock`. The blindfolded,
one-handed, FMC and multi variants reuse another event's puzzle and would
duplicate its scramble, so they are excluded rather than given a board that
looks separate but is not.

## Access control

The threat model has not changed since the sync spec: the anon key ships in
the bundle, so RLS and the `security definer` functions are the entire
boundary. What has changed is that some rows are now deliberately public, so
each table needs its exposure stated explicitly.

```sql
alter table daily_scrambles enable row level security;
-- Deliberately no policy: unreachable except through security definer code.

alter table daily_attempts enable row level security;

-- You always see your own attempt, including before you submit.
create policy attempts_select_own on daily_attempts
  for select using (auth.uid() = user_id);

-- Everyone signed in sees submitted, published attempts. An unsubmitted
-- attempt stays private, so a revealed-but-unfinished solve is not visible
-- as a gap on the board.
create policy attempts_select_board on daily_attempts
  for select using (published and submitted_at is not null);

-- No insert, update or delete policy: writes go through the functions only.
```

`daily_bests` gets the same pair of select policies, plus insert and update
for the owner, since the client maintains it directly as solves change. Its
`with check` must also assert the opt-in, or a client could simply set
`published = true` on its own row:

```sql
create policy bests_write_own on daily_bests
  for all using (auth.uid() = user_id)
  with check (
    auth.uid() = user_id
    and (not published or exists (
      select 1 from profiles p where p.user_id = auth.uid() and p.opted_in
    ))
  );
```

The same reasoning applies in `submit_daily`, which reads the opt-in itself
rather than accepting it as an argument.

Reads of the board resolve usernames with a **second query**, not a PostgREST
embedded select. `daily_attempts.user_id` and `profiles.user_id` both
reference `auth.users(id)`, and there is no foreign key between the two
tables, so PostgREST cannot embed one in the other — an embed fails at
runtime with "could not find a relationship". Adding that foreign key is the
wrong fix: profile rows are created when a username is claimed, so it would
block challenge attempts from anyone who never claimed one. The client joins
by `user_id` instead and falls back to a placeholder name.

`profiles` exposes `username` and nothing else; email stays in `auth.users`,
which is not reachable through PostgREST.

### `reveal_daily(event text)`

`security definer`, `auth.uid()` scoped. In one transaction:

1. Do **not** check the opt-in. Opting in governs whether a result is
   published, not whether you may take part; someone should be able to do the
   daily privately.
2. `insert into daily_attempts (user_id, event, utc_day)
   values (…, (now() at time zone 'utc')::date) on conflict do nothing`.
   Explicitly UTC: `current_date` follows the session timezone, which is a
   setting rather than a guarantee.
3. Return the scramble, plus `revealed_at` and whether a submission exists.

Calling it twice is safe and returns the same scramble: the commitment is the
insert, and the conflict clause makes it idempotent. There is no way to read
the scramble without the row existing first.

### `submit_daily(event text, time_ms int, penalty text)`

`security definer`, `auth.uid()` scoped:

1. Reject if no attempt row exists — you cannot submit a scramble you never
   revealed.
2. Reject if `submitted_at` is already set. **The result is immutable.** That
   is the whole point of one attempt, and it removes the retraction problem
   for the ranked column entirely.
3. Reject if `time_ms` exceeds the wall-clock seconds since `revealed_at`,
   which is impossible rather than merely suspicious.
4. Set `submitted_at = now()`, the time, the penalty, and `published` from the
   caller's opt-in.

### What this does not prevent

A client can still submit a time it did not achieve. Nothing running in a
browser can prevent that, and this design does not pretend otherwise. What it
buys is that everyone faced the same case, that the case was hidden until
commitment, and that `revealed_at → submitted_at` is recorded for every row,
so implausible entries are reviewable after the fact. A takedown is a manual
`update daily_attempts set published = false`.

## Client flows

### Revealing

The challenge is a distinct mode, not a change to the timer's default
behaviour. Entering it for an event you have not attempted shows the
commitment screen — the scramble is not fetched until the button is pressed,
so it cannot be read from devtools beforehand.

On reveal: call `reveal_daily`, show the scramble, and put the timer into
challenge mode. The result is saved to the local store as an ordinary solve,
with **no new column on `solves`** — the attempt row is the authoritative
record of the challenge, and adding a field to a synced table for a label
would change the sync schema for no benefit. The solve list therefore shows
it as a normal solve; the board is where it is identified as the challenge.

### Submitting

Submission is a second, independent write, and it must not be able to lose a
result:

- On stop, write the solve locally first (as today), then call `submit_daily`.
- On network failure, queue the submission in `localStorage` and retry on the
  next sync tick. The attempt row already exists server-side, so a retry can
  always complete.
- If the retry is rejected as already-submitted, drop the queued item; the
  first write won.

Offline, `reveal_daily` cannot be called, so the challenge is unavailable and
says so. Ordinary timing is unaffected. This is the one part of the app that
requires the network, and it is stated plainly in the UI rather than failing
quietly.

### Maintaining `daily_bests`

On each sync tick, recompute the best non-DNF solve for the current UTC day
per event from the local store and upsert it. Because it derives from local
state every time, deleting or DNF-ing the underlying solve corrects the row on
the next tick without any special retraction path. Rows for past days are left
alone.

### The board

One screen, event-selected, showing rank, username, challenge time, and best
today, with the day's scramble displayed above it once you have attempted (or
after the day closes). Your own row is highlighted, and a row for someone who
has not attempted simply is not present.

## Testing

The parts that can be unit-tested in vitest are the pure ones: UTC day
derivation across a boundary, the "best today per event" reducer, and the
submission queue's retry and drop rules.

Everything else is access control, which vitest cannot reach. This phase
carries an **adversarial RLS harness** — a script driving two real accounts
against the API, asserting:

- B cannot select A's `solves`, `sessions`, or unsubmitted `daily_attempts`.
- Nobody can select `daily_scrambles` directly, with or without an attempt.
- `submit_daily` rejects a second submission, a submission with no attempt,
  and a time longer than the elapsed wall clock.
- A user who has not opted in never appears in a board query.
- No query path returns an email address.

This harness is the deliverable that makes phase 3 safe to build, and it
should fail loudly in CI before any policy change ships.

## Rollout

1. Schema and policies, applied with the existing `npm run schema` script.
2. RLS harness, red against the empty schema, green once policies land.
3. Edge Function plus its schedule; verify a scramble appears for each event.
4. Client: board (read-only) first, then reveal and submit.

The Edge Function is the only piece with a deploy target outside Vercel and
should be stood up early, before the client work depends on it.

## Risks

- **The Edge Function is new ground.** cubing.js under Deno with wasm is
  unproven here, and this project has already been bitten once by cubing.js
  behaving differently under a bundler. Spike it before committing to the
  rest.
- **A missed day breaks the board silently.** If the schedule fails, there is
  no scramble and reveal fails. Generation should be lazy as well as
  scheduled: if today's row is missing when someone reveals, generate it then.
- **Opt-in is a promise.** Every board query must filter on `published`, and
  the harness must assert it, because the cost of getting it wrong is
  publishing someone's times without consent.
- **Immutability will generate complaints.** A misscramble or an interruption
  costs the day. That is the deliberate trade for a comparable board, and the
  UI has to say so before the reveal, not after.
